# Project Proposal: Saudi Dialect to Modern Standard Arabic Rewriter with a Fact-Preservation Check

NLP Applications, KAUST Academy (2026 MOI cohort). Topic 6, own project, option A. Date: 19 November 2026. Revised 24 November 2026 after the instructor's feedback (`docs/INSTRUCTOR_FEEDBACK_RESPONSE.md`).

## Idea and goal

A small language model, fine-tuned with LoRA, rewrites short messages written in Saudi dialect into formal Modern Standard Arabic (MSA). A checker then compares the numbers, dates, times, days, listed places and listed names of the message with those of the rewrite.

- **Service:** the booking-support desk of Darb Aljawza Travel (وكالة درب الجوزاء للسفر), a travel agency invented for this project; no real organisation's messages are used. Customers write to the desk in a chat. Messages are of six kinds: new booking, change, cancellation and refund, enquiry, complaint and follow-up, extras.
- **Users:** the staff at that desk. A customer writes in Saudi dialect; the staff member needs the message as a formal written request in MSA, which is filed with the booking and sent on to the supplier (an airline, a hotel).
- **One job:** a dialect message goes in, and the same message in formal MSA comes out, with no fact changed and none added.
- **Missing information:** a request to book that gives no date or no destination, or a request about an existing booking that gives no booking reference, is not rewritten. The system returns the question to ask the customer.
- **Why fine-tune:** we expect a prompted small model to leave dialect words in place and to alter or drop details. The before-and-after comparison will test this.
- **Why local:** messages from the public should stay on the organisation's own machines.
- **Goal:** more messages rewritten correctly than the untuned model with a full prompt, and fewer released outputs with a changed fact. Numerical targets will be selected and documented before the plan review, without presenting unmeasured outcomes as results.

## Dataset

- **Training:** the multidialectal parallel Arabic corpus by Khalid Almeman (Data, 2025), which pairs MSA with five dialects including Saudi: 50,010 rows in the travel and tourism domain ([paper](https://www.mdpi.com/2306-5729/10/12/208), [data](https://doi.org/10.5281/zenodo.17776617)). The Zenodo record and the paper state CC BY 4.0; the README inside the record states a non-commercial licence, so we treat the data as non-commercial. We use the Saudi–MSA pairs. The corpus was generated by a large language model, only a sample was checked by people, and it contains almost no numbers, so we add template pairs with numbers, dates, times and codes and report both points as limitations.
- **Golden test:** 100 dialect messages, most of them containing numbers, dates, times or names, each with a reference MSA version. The examples were AI-drafted and subsequently team-approved through a 25-per-member reciprocal review according to the leader. The test file was committed on 20 November 2026 (commit `eb809ee`), before any training. See the approval record for evidence details.
- **Golden test for the travel desk (v3, draft):** release v2.2 covers general service topics. A draft of 100 travel-desk messages (`data/golden_v3_draft.jsonl`, 12 of them taken or adapted from v2.2) labels the key facts of the messages and, for 40 messages, the needed detail that is missing. It replaces v2.2 only after two members have signed every row, and before any training.
- **Separation:** a script removes every training sentence that equals, nearly equals or contains a golden sentence, then verifies that no overlap remains.

## Type of training

Supervised fine-tuning with LoRA (PEFT) of `Qwen/Qwen3-1.7B`, which is inside the 4B-parameter limit. The training data is in chat format, and the loss is computed on the answer only. Training runs on a Google Colab T4 GPU, with QLoRA (4-bit) as the fallback if memory is short. The adapter will be published on the Hugging Face Hub with a model card.

## System

The model works inside a pipeline that runs on the team's own machine. Before the model is called, a rule-based check looks for a needed detail that the message does not give (date, destination, booking reference); if one is missing the pipeline stops and returns the question to ask. First, the tuned model, served locally by Ollama, rewrites the message into MSA. Second, a checker extracts the numbers, dates, times, Latin-script words, days, months and listed places from the original and from the rewrite and compares them, and confirms that names listed by the user are still present. Third, if they differ, the pipeline asks the model for one repair with the missing facts listed. Fourth, if the repair still fails, the output is withheld and the original message is returned with a warning, so a difference the checker can read is never released silently. What the checker cannot read (a number written in words, a travel class, a place outside its list) is measured with the labelled key facts. A Streamlit app with right-to-left display shows the original, the rewrite, the checker's result and a before-and-after comparison.

## Evaluation

We score three systems on the golden test: the untuned model with a full prompt, the tuned model alone, and the tuned model inside the pipeline. A rewrite counts as correct only if it passes four checks: all facts preserved (automatic), no dialect word left (word list plus review), meaning preserved (two members judging independently), and no labelled key fact lost or changed (the same two members). We count twelve error types: no output, withheld, dropped fact, changed fact, added fact, name lost, dialect word left, input copied without rewriting, meaning changed, content added, key fact lost, and raters disagree. To report what the checks miss, we list every labelled key fact that is lost or changed in a rewrite the pipeline released, we judge the withheld rewrites as well and count those withheld without need, and we score the missing-information check against the labels of the golden test. We also count the examples that moved from wrong to right and from right to wrong. For the full system we report the share of released outputs with a changed fact and the share of messages withheld. Ten adversarial inputs of different kinds form the safety check.
